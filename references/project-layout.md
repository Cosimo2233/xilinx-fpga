# 工程组织与迁移

用于新建工程、引入外部代码或整理已有工作区。先确认依赖和用户指定的项目边界，再决定目录调整。

## 按需采用的目录示例

```text
project/
  README.md          正式入口、版本要求、构建与验证方式
  rtl/               手写 RTL
  hls/               HLS 源码与参考实现
  sim/               测试平台、行为检查及必要输入
  constraints/       引脚和时序约束
  ip/                必要的自定义/第三方 IP 定义及来源说明
  scripts/           创建、构建、仿真、导出脚本
  sw/                系统所需的固件或配套应用
  docs/              接口、板级依据和工程验证说明
  build/             生成的工具工程、缓存、中间文件和运行日志
  artifacts/         对应构建的部署产物与必要清单
```

这是目录职责示例。没有 HLS 或软件时不创建相应空目录；已有清楚且可构建的结构可直接沿用。
Vivado 工程也可放在独立的 `vivado/` 目录；README、启动脚本和源码引用必须一致。
Vitis 的工作区或组件入口按实际版本说明，避免并列多个容易混淆的正式入口。

## 文件归属与版本管理

| 内容 | 处理方式 |
|---|---|
| RTL、HLS、XDC、Block Design 定义及构建脚本 | 作为工程来源管理，明确哪份定义是重建依据 |
| 初始化数据、必要测试向量和基准输入 | 保留为可追溯输入，避免被宽泛的忽略规则遗漏 |
| 第三方 IP | 记录来源、版本和必要许可说明；提供依赖获取方式或按许可保留所需文件 |
| HLS 导出的 IP、生成 HDL、工具缓存 | 作为生成依赖管理；删除前确认有可运行的生成链路 |
| 配套固件和应用 | 按系统需要组织，接口和版本明确；仓库拆分遵循用户选择 |
| 运行日志及中间文件 | 集中放在构建目录；必要的验证证据可随工程说明保存 |
| bitstream、平台交接及部署文件 | 归入交付产物，说明来源构建及使用场景 |
| 外部原工程、竞赛报告、无关媒体资料 | 按任务要求放在独立资料或归档位置，保留来源关系 |

不要只因为工程引用了生成文件，就删除这些文件来获得“整洁”目录。
直接打开的 `.xpr` 可能依赖生成的 IP、HDL 或数据；提供现成可打开工程时，要保证依赖可用。
从源码重建时应能重新产生这些依赖，不能要求用户猜测缺失步骤。
Vitis 使用的 XSA 是硬件交接文件；软件还可能需要其平台、BSP、域或操作系统构建配置。

## 整理已有工程

1. 记录正式工程、已有修改、构建状态、关键产物位置及工具进程。识别 Git worktree、虚拟环境和工具工作区的路径绑定。
2. 追踪 `.xpr`、BD/Tcl、IP 配置、HLS 项目、约束、软件配置及启动脚本中的引用，列出实际待迁移项及目标位置。
3. 优先处理无依赖的旧入口、散落日志和明确的历史资料。迁移必要源码或 IP 时，同步修改生成脚本和工程引用；不要仅改生成文件中的路径。
4. Windows 移动目录前核验源与目标的规范化绝对路径处于指定工作区或用户明确指定的位置；使用同一 shell 的原生命令处理。
5. 不在用户正在编辑的工程或仍运行的任务下移动其依赖。可先整理外围目录；必要的工作区迁移使用对应工具支持的方式处理路径绑定。
6. 整理后检查正式入口与依赖存在，打开工程、核验顶层和文件集，再执行受迁移影响的构建步骤。代码未变时用产物校验值确认移动未改动内容。
7. 更新 README、构建脚本的输出位置和部署说明；避免旧入口仍被描述为正式工程。

单纯移动完整交付文件通常只需校验文件与配套关系；改变源码、IP、约束或生成路径时，需要重新验证相关构建链路。
